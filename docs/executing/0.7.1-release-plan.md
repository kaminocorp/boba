# 0.7.1 Release Plan

**Goal:** Cut the first real Boba release. The codebase is at changelog v0.7.1 (MCP server hardened, 840 tests green) but `pyproject.toml` still says `0.2.9` and no git tag has ever been pushed. This plan walks the project from "code-complete" to "installable artifact."

**Scope:** Distribution only. No new features, no behaviour changes. If a step uncovers a bug, fix it in a separate commit before continuing.

## Step 1 — Version bump

**File:** `pyproject.toml:7`

Change `version = "0.2.9"` → `version = "0.7.1"`.

**Why this version, not 0.7.2 or 1.0.0:** the changelog already documents 0.7.1 with date `2026-04-06`. The release should match the changelog, not invent a new number. There is no prior published artifact, so jumping straight from "unreleased 0.2.9" to "released 0.7.1" is correct — there is nothing in the wild to break.

**Decide:** do we want a single commit "Bump version to 0.7.1" or fold it into Step 4's tag commit? Recommend a standalone commit so the tag points to a commit whose only purpose is the version bump — easier to cherry-pick or revert.

## Step 2 — Audit `mcp` extra and `boba-mcp` entry point

**Concern raised in prior discussion:** `pyproject.toml:32` registers `boba-mcp = "boba.mcp:main"` unconditionally, while the `mcp` package is gated behind the `[mcp]` extra. A user who runs `pip install boba` (without the extra) and then types `boba-mcp` will hit an `ImportError` at script entry rather than a clean message.

**Action:**

1. Read `src/boba/mcp/__init__.py` and confirm whether `main` already guards the `import mcp` (or `fastmcp`) call with a try/except + friendly error.
2. If it doesn't, wrap the import in `__init__.py:main()` so the failure mode is:
   ```
   boba-mcp requires the 'mcp' extra. Install with:
       pip install 'boba[mcp]'
   ```
3. Add a single test that imports `boba.mcp` *without* the optional dep stubbed and asserts the friendly error path. (Or, if too invasive, document the limitation in the README and skip the test.)

**Decision needed:** is this in scope for 0.7.1 or deferred to 0.7.2? Recommend **in scope** — it's a release-blocking UX cliff for new installs and is a ~10-line fix. If deferred, at minimum add a one-line note to the README install section.

## Step 4 — Build the artifact locally

Before tagging, confirm the wheel actually builds and is installable into a fresh environment.

```bash
# From repo root
python -m build              # produces dist/boba-0.7.1-py3-none-any.whl + sdist
```

If `build` is not installed: `pip install build`.

**Smoke test in a throwaway venv:**

```bash
python -m venv /tmp/boba-smoke
/tmp/boba-smoke/bin/pip install dist/boba-0.7.1-py3-none-any.whl
/tmp/boba-smoke/bin/boba --help            # CLI works
```

**Expected gotchas:**
- `playwright` is a hard dep — `pip install` succeeds but the browser binaries are not downloaded automatically. Document this in the README install block: users must run `playwright install chromium` after install. If not already documented, add it.

- `gitleaks`, `nuclei`, `subfinder`, etc. are external binaries, not Python deps — `find_binary()` handles missing-binary errors at runtime. No release action needed, but worth a sentence in the README about prerequisites.

## Step 6 — PyPI publication (optional, decide before executing)

**Decision needed up front:** is Boba going to PyPI, or staying GitHub-install-only (`pip install git+https://github.com/...`)?

Arguments for PyPI:
- `pip install boba` is the universal install verb — agents/tools that consume Boba via MCP will expect it.
- The package name `boba` is currently checked into the project; need to confirm it's available on PyPI (it may collide with an existing package — `boba` is a common name).

Arguments against (for now):
- Once on PyPI, any version is permanent. A bad release can't be deleted, only yanked.
- Requires a PyPI account, API token, and 2FA setup.
- Locks in the package name `boba` — if it's taken, you'll discover that here and have to rename, which cascades through imports, scripts, docs.

**If proceeding with PyPI:**

1. Check name availability: `pip index versions boba` or visit `https://pypi.org/project/boba/`. If taken, stop and rename (large change — separate plan).
2. Use **TestPyPI first**: `twine upload --repository testpypi dist/*`, then `pip install --index-url https://test.pypi.org/simple/ boba` in a fresh venv. Confirm `boba --help` and `boba-mcp --help` work.
3. Real upload: `twine upload dist/*`.
4. Verify: `pip install boba==0.7.1` in a clean venv.

**Recommendation:** defer PyPI to a separate decision/session. Cut the git tag in this release; publish to PyPI only after confirming the name is free and a TestPyPI dry-run is clean.

## Rollback plan

If a problem is discovered *after* the tag is pushed but *before* PyPI:
- Delete the local tag: `git tag -d v0.7.1`
- Delete the remote tag: `git push origin :refs/tags/v0.7.1` (destructive — confirm with user)
- Fix the issue, re-tag.

If a problem is discovered *after* PyPI upload:
- **Cannot delete.** Yank the release on PyPI (`pip install` won't pick it up but `pip install boba==0.7.1` still works for anyone who pinned it).
- Cut `0.7.2` with the fix.
